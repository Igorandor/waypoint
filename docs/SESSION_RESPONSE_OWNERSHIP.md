# Session ownership of pending responses

The client previously accepted responses without recording which browser session started them. A late 401 from an earlier login could close the new login's UI. A delayed initial session response could overwrite the new CSRF token, including the discarded initial effect under React StrictMode. An asynchronous observation could also continue polling its earlier job after another account signed in.

The API client now captures a local generation for each request. Login and logout attempts invalidate earlier generations; successful completion also invalidates reads started while that transition was pending. A current protected-request 401 clears the token and ends the current generation before body parsing, including an unreadable error body. Responses are checked before decoding and again afterward, before returning data or changing CSRF. A discarded response raises a local earlier-session error without emitting another session-ended event. Initial `/session` reads do not advance the generation, so duplicate startup reads remain valid in either completion order. The native async observation loop keeps its original generation and checks it before another poll.

A same-origin BroadcastChannel sends only the fixed `session-changed` message after successful login/logout or a current protected-request 401. Other open Waypoint tabs clear their generation/token and use the existing session-ended event to unmount protected views. They do not silently sign in as the new account, transmit account data or tokens, or rebroadcast received messages. Browsers that do not support or permit BroadcastChannel retain local request ownership checks but cannot receive this cross-tab notification.

The change does not undo or automatically retry an operation that has already reached the server. Discarding an earlier-session response is not evidence that a native write was canceled. Previously downloaded files are not client caches and are unaffected.

## Controlled regression coverage

`tests/session-generation.test.ts` uses the actual client with a promise-controlled fetch transport. It covers late successful/401 responses, late decoded CSRF, current 401 and pending peers, malformed 401 bodies, reads begun during login/logout transitions, logout token handling, duplicate initial reads in both orders, stopped old-job polling and normal current-session polling. Before the fix, five of the initial six scenarios failed; normal polling passed. Subsequent regressions also reproduced the unreadable-401 and pending-logout gaps before their fixes.

`tests/session-broadcast.test.ts` compiles the actual client into two independent module/global contexts with a controlled channel. It verifies peer invalidation, pending data rejection, token clearing, current 401, a successful new login, ignored unrelated messages and absence of rebroadcast/data-bearing messages. Running the peer logout scenario against the prior committed client produced zero peer invalidations instead of one. These are simulated browser contexts, not a claim of completed desktop/mobile browser verification. No regression contacts IRIS or starts a listener.

The implementation task did not modify a running gateway, rebuild a container, change native data or make a commit. Real-browser evidence is recorded separately by the integration review.

Final validation on 2026-09-27: `npm run check` passed (TypeScript, production build and 197 tests, including twelve new session regressions).

Integration browser verification on 27 September 2026 used the current production client in two same-origin tabs with synthetic accounts FixtureA/FixtureB.
